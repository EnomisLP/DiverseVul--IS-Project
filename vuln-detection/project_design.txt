1. IDEA DEFINITION & THEORETICAL FOUNDATION
--------------------------------------------------------------------------------
The primary objective of this project is to research, design, and evaluate an
Intelligent System (IS) capable of predictive software vulnerability detection
directly within C/C++ source code. As open-source and proprietary software
ecosystems expand, manual code auditing and legacy static application security
testing (SAST) tools fail to capture complex, multi-line semantic flows that
signal exploitable vulnerabilities. This project addresses these limitations
by framing vulnerability detection as a binary sequence classification problem,
and compares two families of approach on the same dataset and the same
evaluation protocol:

Case Study 1: The Classical Lexical Pipeline
This pipeline relies on explicit lexicon-based representations extracted from
source code tokens (word- and character-level TF-IDF, plus a deterministic
structural feature vector), routed into two classical/shallow classifiers: a
class-weighted L2 Logistic Regression and a shallow Multi-Layer Perceptron
(MLP). This decouples the representation step entirely from the downstream
classification model.

Case Study 2: The Deep Representation Pipeline (NeoBERT)
This pipeline explores deep semantic embeddings via NeoBERT, a 250M-parameter
bidirectional transformer encoder. Two ways of adapting the pretrained
backbone to this task are compared:
  - A frozen-encoder linear probe: NeoBERT's weights are never updated; a
    mean-pooled sentence embedding is classified by a logistic regression
    probe trained on top.
  - LoRA (Low-Rank Adaptation) fine-tuning: NeoBERT's attention projections
    are adapted via low-rank update matrices, expressed as
    W = W_0 + Delta_W = W_0 + (B x A), while the base weights stay frozen.
    Only the low-rank adapters (and the classification head) are trained.

--------------------------------------------------------------------------------
2. IDENTIFICATION OF THE ML/AI TASK(S)
--------------------------------------------------------------------------------
The vulnerability detection problem is mapped to the following core Machine
Learning task:

Primary Task: Binary Classification
  - Description: The system ingests one C/C++ function and computes a
    probability indicating whether it contains a known vulnerability.

  - Input Formalization (Case Study 1):
    A fixed-length numeric vector combining word-level TF-IDF, character-level
    TF-IDF, and (for the MLP) a 54-dimension deterministic structural feature
    vector, all extracted from the function's identifier-abstracted text (see
    Section 4.4 for the full specification).

  - Input Formalization (Case Study 2):
    The function's normalized (or identifier-abstracted) text, tokenized into
    a numeric array of token IDs and an attention mask, truncated/padded to a
    fixed 512-token context window.

  - Output Formalization:
    A discrete binary label Y in {0, 1} and a continuous confidence score P:
        Y = 1: the function contains a vulnerability.
        Y = 0: the function is secure.
        P: a scalar in [0.0, 1.0], the model's predicted probability of Y = 1.
           This is a risk-ranking score derived from a class-weighted
           objective, not a calibrated real-world probability.

3. SELECTION OF A SUITABLE DATASET
--------------------------------------------------------------------------------
The dataset used for model training, cross-validation, and benchmark testing
is RDiverseVul (Refined DiverseVul), a cleaned derivative of the original
DiverseVul dataset (Chen et al., RAID 2023).

KDD Phase Alignment:
  - Data Selection and Initial Preprocessing.

Justification:
The original DiverseVul dataset was a significant step forward in size, but
contained data-quality anomalies that limit high-capacity neural models:
comment-only code snippets, identical function declarations with conflicting
vulnerability labels (label noise), and structural duplication. RDiverseVul
remediates these issues by filtering out erroneous duplicate entries, yielding
a higher-fidelity security baseline.

This project evaluates on the natural, imbalanced class distribution (~5.6%
positive) rather than a class-balanced subsample, and uses a project-grouped
cross-validation protocol (no function from the same repository ever appears
in both the training and the test portion of a fold). This matches the
original DiverseVul paper's harder "unseen-project" evaluation scenario: a
model that has never seen a project's coding style or conventions is
evaluated on new functions from that same project.

Given the compute cost of the full experimental matrix (Section 6) across
five rotating cross-validation folds, the ~200,000+ row dataset is
stratified-downsampled to approximately 20,000 rows (preserving the original
~5.6% positive rate exactly), and every experiment trains and evaluates on
this downsampled dataset.

--------------------------------------------------------------------------------
4. ANALYSIS AND EXPLORATION OF THE IDENTIFIED DATASET (EDA)
--------------------------------------------------------------------------------
KDD Phase Alignment:
  - Data Cleaning, Exploratory Data Analysis, and Data Transformation.

4.1 Class Imbalance Analysis
  - Real-world software repositories exhibit extreme class skew; secure
    functions vastly outnumber vulnerable ones. The measured positive rate on
    the (downsampled) dataset is ~5.6%.
  - Mitigation: class-weighted training objectives are applied uniformly
    across every experiment (BCEWithLogitsLoss with pos_weight = negative /
    positive count for Case Study 2; class_weight='balanced' for Case Study
    1's Logistic Regression and Case Study 2's linear probe), so the minority
    (vulnerable) class exerts sufficient optimization pull.

4.2 Sequence Length Distribution
  - Legacy sequence models are constrained by small context windows,
    forcing truncation of large functions. The large majority of RDiverseVul
    functions fall under 512 tokens, so a max_sequence_length of 512 is used
    for NeoBERT, even though its architecture natively supports up to 4,096
    tokens via Rotary Position Embeddings (RoPE) with the YaRE extension.

4.3 CWE Distribution
  - "Vulnerability" is an aggregate term encompassing distinct classes of
    coding error, catalogued via Common Weakness Enumeration (CWE)
    identifiers. Memory-safety-relevant CWE families (e.g. CWE-119, CWE-787,
    CWE-476, CWE-125) are of particular interest given the C/C++ domain, and
    are examined descriptively as part of the dataset's characterization.

4.4 TEXT PREPROCESSING AND CASE STUDY 1 FEATURE SPECIFICATION

  Preprocessing is deterministic and row-independent (it depends only on a
  function's own text, never on labels or on other rows), so it runs once on
  the whole dataset, before any train/test split. It produces two parallel
  text representations, compared side by side throughout the experimental
  matrix:

  a) Normalization (normalized_code): whitespace collapsing, line-ending and
     blank-line normalization, applied via a hand-written C/C++-aware lexer
     that recognizes string/char literals, comments, and identifiers so that
     normalization never alters literal contents. Comments are preserved.

  b) Identifier abstraction (abstracted_code_v1): built on top of (a) via
     SCoPE2, a tree-sitter-based structural transformation tool. It removes
     comments and replaces user-defined variable and function names with
     anonymized placeholders, while preserving C/C++ keywords, standard
     types, standard-library API names, numeric literals, and all
     operators/punctuation/line structure. This is a deliberate anti-leakage
     control: it prevents downstream lexical models from memorizing
     project-specific naming conventions instead of learning genuinely
     predictive lexical/structural patterns -- directly relevant given the
     project-grouped evaluation protocol.

  Attribute selection (fitting TF-IDF vocabularies and, for the MLP, fitting
  TruncatedSVD) is a separate step that happens strictly after the
  cross-validation split, fit on each fold's training partition only, and
  applied (transform-only) to that fold's test partition. This preserves the
  standard "attribute selection after the split" ordering: preprocessing
  reduces the raw dataset, cross-validation splits it, and only then is any
  data-dependent feature-selection step fit.

  Case Study 1 feature extraction (downstream of preprocessing):
    a) Word-level TF-IDF over the (normalized or abstracted) token stream,
       n-grams n in {1,2,3}, min_df and max_features selected per outer fold
       via inner cross-validation (Section 6.2). Used by both Logistic
       Regression and the MLP.
    b) Character-level TF-IDF, n-grams n in {3,4}, min_df and max_features
       likewise selected via inner cross-validation. Captures morphology that
       word n-grams miss (e.g. pointer/array syntax, partial identifiers).
       Concatenated with (a) via sparse hstack.
    c) A 54-dimension deterministic structural/statistical feature vector,
       computed directly from the source text: identifier and unique-
       identifier counts, control-flow keyword counts (if/else/for/while/
       switch/goto/...), function-call counts, a cyclomatic-complexity proxy,
       brace/parenthesis/array-access counts, pointer-declaration and
       cast-like-pattern counts, and categorized standard-API call counts
       (memory, string, format, input, allocation/deallocation, assert).
       Used only by the MLP, concatenated onto (a)+(b), after (a)+(b) are
       further reduced to a dense representation via TruncatedSVD.

5. SELECTION OF THE MOST SUITABLE ML/AI MODELS
--------------------------------------------------------------------------------
5.1 Case Study 1 Classifiers
  - Logistic Regression (SGDClassifier, log-loss, L2 penalty)
    * Interpretable, fast, strong baseline for high-dimensional sparse
      lexical features. The L2 strength (alpha) is selected via inner
      cross-validation, per outer fold.
  - Shallow Multi-Layer Perceptron (MLP)
    * Structure: dense input (TruncatedSVD-reduced TF-IDF + 54 static
      features) -> Hidden Layer 1 (ReLU) -> Hidden Layer 2 (ReLU) -> Output
      (1 logit). Hidden layer sizes and learning rate are selected via inner
      cross-validation, per outer fold.
    * Trained with validation-PR-AUC-based early stopping (patience and
      min_delta, best-checkpoint restoration).

5.2 Case Study 2 Model: NeoBERT-250M
  - Specifications: Chandar Research Lab; 250M parameters; 28 layers x 768
    hidden dimensions; RoPE with YaRE; SwiGLU activations; Pre-RMSNorm.
  - Two adaptation strategies are compared on the same backbone:
    * Frozen linear probe: NeoBERT's weights are frozen; a mean-pooled
      sentence embedding (computed once for the whole dataset, since a
      frozen encoder has no train-only fitting step) is classified by an
      L2-regularized Logistic Regression, with the regularization strength
      (C) selected via inner cross-validation, per outer fold.
    * LoRA fine-tuning: NeoBERT's attention projections are adapted via
      low-rank matrices (rank 16, alpha 32 -- the standard alpha = 2 x rank
      convention -- learning rate 2e-4, all fixed at literature-standard
      values for encoder models of this size rather than searched, to keep
      fine-tuning within a practical compute budget). Trained with
      validation-PR-AUC-based early stopping, epochs capped at a ceiling
      rather than run for a fixed count.

  Technical safeguards applied to NeoBERT:
    1. Pooling and the classification head run in explicit float32
       regardless of the ambient autocast dtype, to prevent a bf16/fp16
       NaN/Inf produced upstream in NeoBERT's attention stack from being
       baked into the trainable head via a half-precision matmul. Frozen
       embeddings are additionally checked for finiteness at extraction
       time, failing loudly rather than silently propagating corrupted
       values downstream.
    2. NeoBERT's fused flash/memory-efficient scaled-dot-product-attention
       backends are disabled in favor of the reference (math) backend, and
       sequence unpadding is disabled, both to guarantee correct, stable
       attention on padded, variable-length batches.

6. DESIGN, TEST, AND COMPARISON OF THE SELECTED MODELS
--------------------------------------------------------------------------------
This phase executes the Pattern Evaluation stage of the Knowledge Discovery
in Databases (KDD) process through a strictly partitioned experimental
matrix.

6.1 EVALUATION PROTOCOL: ROTATING, PROJECT-GROUPED, STRATIFIED 5-FOLD CV
  - A single manifest is built once, on the (downsampled) dataset, via
    scikit-learn's StratifiedGroupKFold(n_splits=5), grouped by source
    repository ("project") and stratified by label. No function from the
    same project ever appears in both the training and test portion of the
    same fold. This manifest is shared identically by all four experiments.
  - There is no separate fixed holdout partition: every one of the 5 folds
    takes a turn as the test set, with the other 4 folds forming that
    iteration's training partition.
  - Nested hyperparameter search: for each outer fold, every hyperparameter
    that needs choosing is selected via an inner, project-grouped,
    stratified 3-fold cross-validation on that outer fold's training
    projects only -- the outer test fold is never used for model selection.
    Candidates are ranked by pooled (micro-averaged) inner-validation PR-AUC:
    every inner fold's held-out predictions for a given candidate are
    concatenated into one set before the metric is computed once, rather
    than averaging metrics computed separately per inner fold. This matters
    because PR-AUC is rank-based, not additive across folds: with a rare
    positive class, a per-fold score can be dominated by how few positive
    examples that one fold happens to contain, and averaging such noisy
    per-fold scores (macro-averaging) is a biased proxy for how the
    candidate would perform on a genuinely larger evaluation set. Pooling
    first (micro-averaging) avoids this.
  - The decision threshold is likewise selected only from inner-validation
    predictions (maximizing F1 over a fixed grid), never from the outer test
    fold.
  - Once hyperparameters are selected, the winning configuration is refit on
    the outer fold's entire training partition, and scored exactly once on
    that fold's held-out test partition.
  - Headline result: mean and standard deviation of each metric across the 5
    outer folds. Pooled out-of-fold metrics (every row scored once, by
    whichever fold's model did not train on it) are reported as a secondary
    cross-check, together with a 95% confidence interval from a project-
    block bootstrap (1,000 resamples of whole projects with replacement,
    percentile method) on the pooled PR-AUC. Cross-experiment differences
    are assessed via a paired project-block bootstrap over the same pooled
    predictions.

6.2 EXPERIMENTAL MATRIX

  - CASE STUDY 1: CLASSICAL LEXICAL PIPELINE (feature set: Section 4.4)
    * EXP-1: Logistic Regression
      - Word + character TF-IDF (capacity and min_df searched per outer
        fold) mapped to a class-weighted L2 Logistic Regression (SGD, log
        loss; L2 strength searched per outer fold).
    * EXP-2: Shallow MLP
      - Word + character TF-IDF, reduced via TruncatedSVD, concatenated with
        the 54-dimension static feature vector, mapped to the MLP specified
        in Section 5.1. Hyperparameters are searched in two stages per outer
        fold: first the representation (TF-IDF capacity and SVD component
        count, architecture held at a default), then the architecture
        (hidden layer sizes and learning rate, representation fixed at the
        Stage 1 winner) -- this keeps the joint search space tractable
        without having to try every representation/architecture combination.

  - CASE STUDY 2: NEOBERT PIPELINE
    * EXP-3: Frozen Backbone Linear Probe
      - NeoBERT embeddings, frozen, mean-pooled once for the whole dataset;
        classified via Logistic Regression with the regularization strength
        (C) searched per outer fold.
    * EXP-4: LoRA Fine-Tuning
      - NeoBERT attention projections adapted via LoRA at a fixed rank
        (Section 5.2). Inner cross-validation is used only to calibrate the
        decision threshold at this fixed configuration, since rank, alpha,
        and learning rate are fixed at literature-standard values rather
        than searched.

  Both preprocessing variants (normalized_code and abstracted_code_v1, see
  Section 4.4) are run through all four experiments and compared side by
  side, giving 4 experiments x 2 variants = 8 reported runs.

6.3 EVALUATION METRICS
Due to severe class imbalance, accuracy is not used. Performance is reported
via:
  - Precision: TP / (TP + FP) -- minimizes false alarms.
  - Recall: TP / (TP + FN) -- minimizes missed vulnerabilities.
  - F1-Score: harmonic mean of precision and recall, at the selected
    decision threshold.
  - PR-AUC (Average Precision): area under the precision-recall curve;
    the primary, threshold-independent metric used for model selection and
    for reporting the headline mean +/- standard deviation result.
